# Requirements Document

## Introduction

A Strauss employee who is eligible for a company car asks: "If I switch to an electric car, take a different car, or give up the car, how much will it change my net pay?" Currently, getting the answer takes three emails and two weeks.

"Strauss Car Advisor" answers that question within a minute: a Hebrew-language bot that collects in conversation only what is missing, invokes tools to retrieve the usage value from the official Israel Tax Authority dataset, to check eligibility and to calculate, and presents a clear, explained comparison between the alternatives and the current situation. When information is missing, the bot asks the employee or sends a question to the transport representative, and the conversation resumes from the same point when the representative answers. The calculation is done in code according to a rules file, not by the language model.

Stack: Python 3.12 + FastAPI + Pydantic AI (OpenAI), Angular, SQL Server, Docker Compose.

The items that were still to come from Strauss (car catalog, occupations table, the car price in the family track, how the EV refund is applied in the payslip, the net pay calculation method, and sample employees with approved net pay) arrived with the challenge update of 2026-10-12, and the requirements below include them. The review of 2026-10-20 then aligned the requirements with the challenge text: the participation of a new catalog car comes from the catalog, the eligibility group comes from the occupation, the catalog's usage values are checked against the dataset, and an occupation in which the car is mandatory has no Today without a car. The data stays in files, so a pilot replaces data and not code.

The payroll parameters are the challenge's 2025 tables, as the challenge's rules file gives them for illustration, while the usage values are those of the tax year 2026 dataset. The years are mixed on purpose, as in the challenge; a pilot enters the tables of its own year.

The app's user-facing copy (UI and bot) is in Hebrew; code and documentation are in English, except the Hebrew Explanations_File.

## Glossary

- **Advisor_App**: All components of the car advisor together (Database, Backend_API and Frontend), which start with a single `docker compose up` command.
- **App_Settings**: The environment variables from the `.env` file (dataset file path, tax year, Database connection, language model provider and model, and the API key); only `.env.example`, without secrets, is kept in Git.
- **Codebase**: All code, tests and configuration files of Advisor_App.
- **Database**: SQL Server in Docker that holds Usage_Value_Dataset, Conversation, Employee_Profile and Rep_Question.
- **Backend_API**: A FastAPI server that exposes the system's capabilities to the Frontend under `/api` routes.
- **Frontend**: An Angular application that contains Employee_Screen and Rep_Screen.
- **Usage_Value_Dataset**: The Israel Tax Authority's car usage value dataset (CSV encoded in windows-1255, 77,988 records for tax year 2026), as loaded into the Database.
- **Official_Key**: Tax year + registration year + vehicle type code + manufacturer code + model code; identifies exactly one record in Usage_Value_Dataset.
- **Usage_Value**: The monthly amount in ₪ that is added to the employee's taxable income for a company car, as listed in Usage_Value_Dataset.
- **Powertrain**: electric, hybrid, plug_in or conventional, according to the electric column of Usage_Value_Dataset.
- **Importer**: The component that loads the Usage_Value_Dataset CSV file into the Database, one tax year per load.
- **Car_Lookup**: The component that retrieves a record from Usage_Value_Dataset by Official_Key and searches for candidate cars by registration year and name.
- **Rules_Config**: The `rules.yaml` file with the challenge rules and the payroll parameters (the challenge's 2025 tables), which can be updated without changing code.
- **Car_Catalog**: Strauss's list of cars: model, manufacturer code, model code, registration year, monthly cost, default Participation, the usage value of the sheet as a check value, and group.
- **Occupations_Table**: For each occupation: its Eligibility_Group, whether the car is mandatory, whether giving up the car is allowed, and the Car_Maintenance amount.
- **Mock_Data**: The challenge's data in Car_Catalog and Occupations_Table, which stand in for Strauss's files and are replaced by swapping a file without changing code.
- **Employee**: A Strauss employee who is eligible for a company car and uses Employee_Screen.
- **Transport_Rep**: The person who answers Rep_Question in Rep_Screen.
- **Eligibility_Group**: A, B, C or D (A = א, B = ב, C = ג, D = ד); determines Car_Budget and the groups in Car_Catalog from which a car may be chosen. The employee's Eligibility_Group is the group of the employee's occupation in Occupations_Table, unless Transport_Rep set another group for the employee (Group_Override).
- **Group_Override**: An Eligibility_Group that Transport_Rep set for one employee in an answer to a Rep_Question, which replaces the group of the occupation for that employee. Only Transport_Rep sets it.
- **Car_Budget**: The monthly car budget per Eligibility_Group, as defined in Rules_Config.
- **Car_Cost**: The monthly cost of a car to the company according to Car_Catalog, also for a car in Family_Track.
- **Employee_Profile**: The collected employee data: base salary, additional pay components, pension and study fund contributions, tax credit points, occupation, number of children up to age 23, the current car and the Participation in it, and the Group_Override when there is one.
- **Today**: The employee's current situation, with the current car and the Participation in it, or without a car, against which the Net_Pay difference is calculated.
- **Alternative**: An option the employee examines against Today: another identified car, or giving up the car.
- **Participation**: The monthly amount the employee pays from salary for the company car.
- **Default_Participation**: The Participation of a car as Car_Catalog lists it, which is the Participation of a new catalog car until Transport_Rep gives another amount for that car.
- **Family_Track**: A track for an employee with 4 or more children up to age 23, in which the employer and the employee split the gap between Car_Budget and Car_Cost 50%/50%, with the employee's share deducted from net pay together with the Participation.
- **EV_Refund**: A monthly net addition of exactly ₪250 (the amount set in Rules_Config) for an employee whose car's Powertrain is electric. The challenge grosses it up so that the employee sees exactly that amount in net pay.
- **Car_Maintenance**: The monthly amount that an employee who gave up the car receives, according to Occupations_Table; it is taxable and not part of the pension base.
- **Unused_Budget**: The difference between Car_Budget and Car_Cost when the cost is lower than the budget; it is not paid as salary.
- **Net_Pay**: The employee's monthly net salary, as calculated by Payroll_Calculator.
- **Eligibility_Checker**: A pure function that checks whether an Alternative is allowed for the employee according to Rules_Config, Car_Catalog and Occupations_Table, and returns a decision and a reason.
- **Payroll_Calculator**: A pure function that calculates monthly Net_Pay according to the challenge's net method and the payroll parameters in Rules_Config.
- **Comparison_Engine**: A pure function that takes Employee_Profile and an Alternative and returns the estimated Net_Pay, the difference from Today, and a breakdown of what changed.
- **Explanation**: Up to two lines of plain Hebrew that explain the Net_Pay difference between an Alternative and Today.
- **Advisor_Agent**: A Hebrew-language conversational agent (Pydantic AI on OpenAI) that collects Employee_Profile and invokes Agent_Tool, and performs no calculations itself.
- **Agent_Tool**: A function that Advisor_Agent invokes, one of six: search and retrieval in Car_Lookup, displaying Car_Catalog by Eligibility_Group, Eligibility_Checker, Comparison_Engine, sending a Rep_Question, and updating Employee_Profile.
- **Rep_Question**: A question that Advisor_Agent sends to Transport_Rep, about missing information or about a value that only Transport_Rep confirms, together with its status and answer. Its type is one of: Participation, occupation, eligibility group, or other.
- **Conversation**: The conversation between Employee and Advisor_Agent, including the readable messages and the agent's serialized message history, stored in the Database.
- **Document_Reader**: An optional component that reads a payslip or contract that the employee uploaded and proposes values from it for Employee_Profile.
- **Employee_Screen**: The screen where Employee chats with Advisor_Agent, corrects data and sees the comparison between the alternatives.
- **Rep_Screen**: The screen where Transport_Rep sees open Rep_Question items and answers them.
- **Explanations_File**: The Hebrew-language explanations document, the one project deliverable written in Hebrew, covering the architecture, folder structure, calculation, running, changing settings, debugging and adding features.

## Requirements

### Requirement 1: Loading the Usage Value Dataset

**User Story:** As a developer who maintains the system, I want to load the Tax Authority's usage value dataset into the Database reliably, so that every calculation is based on the official data as published.

#### Acceptance Criteria

1. WHEN the Importer is run, THE Importer SHALL read the Usage_Value_Dataset CSV file (comma-separated, encoded in windows-1255, with a header row as the first line and one record on each following line) from the path defined in App_Settings, and store Hebrew text, such as the manufacturer name, as the same Hebrew characters that the file contains.
2. WHEN the Importer reads a field from the file, THE Importer SHALL strip the leading and trailing whitespace from the field before parsing or storing the field.
3. THE Importer SHALL store the vehicle type code, manufacturer code and model code as text, exactly as they appear in the file after trimming and including the leading zeros (for example: manufacturer code 01229 and model code 00001 are stored as 01229 and 00001, not as 1229 and 1), which is the same format in which Car_Lookup compares them.
4. THE Database SHALL identify each record in Usage_Value_Dataset by Official_Key as a composite primary key.
5. IF two rows in the file share the same Official_Key, THEN THE Importer SHALL fail and report the duplicated Official_Key and the row numbers of both rows (the first row with that Official_Key and the duplicate row), where a row number is the line number in the file and the header row is line 1.
6. WHEN the Importer reads a row, THE Importer SHALL derive Powertrain from the electric column according to the actual values: 3 = electric, 1 = hybrid, 2 = plug_in, 0 = conventional (the legend in the column header is wrong).
7. THE Importer SHALL store, for each record, the raw value of the electric column alongside Powertrain.
8. THE Importer SHALL derive Powertrain for every row only from the value in the electric column, without correcting that value according to any other column (such as fuel type or engine displacement), including for the approximately 12 rows whose classification in the file appears wrong, treating the value in the file as official data.
9. WHEN the Importer reads the effective date, THE Importer SHALL parse the effective date in dd/mm/yyyy format, day first and month second (for example: 06/01/2020 is stored as 6 January 2020, not as 1 June 2020).
10. THE Importer SHALL store the Usage_Value of each row exactly as the Usage_Value appears in the file, as the same amount in ₪ without rounding, scaling or recalculation (for example: 7990 in the file is stored as ₪7,990).
11. WHEN the Importer loads a tax year, THE Importer SHALL replace all records of that tax year in a single transaction, without changing the records of any other tax year.
12. IF the load fails at any stage (reading or decoding the file, validating a row, or writing to the Database), THEN THE Importer SHALL roll back the transaction and leave the previous records of that tax year, and the records of every other tax year, in the Database unchanged.
13. IF a row in the file is malformed (a number of columns other than 19, an empty value in any field of Official_Key, a value in a numeric field such as the tax year, registration year, list price, adjusted price or Usage_Value that cannot be parsed as a number, an effective date that is not a valid dd/mm/yyyy date such as 31/02/2026, or a value in the electric column other than 0, 1, 2 or 3), THEN THE Importer SHALL fail and report the row number of the first malformed row in file order (the line number in the file, where the header row is line 1) and the reason.
14. WHILE the Database has no records for the tax year defined in App_Settings, WHEN Advisor_App starts with the `docker compose up` command, THE Importer SHALL load that tax year of Usage_Value_Dataset before Backend_API starts accepting requests.
15. WHILE the Database already has records for the tax year defined in App_Settings, WHEN Advisor_App starts, THE Importer SHALL keep the existing records unchanged without reloading the file.
16. WHEN a developer runs the manual load command with a tax year, THE Importer SHALL reload that tax year even if the Database already has records for that tax year.
17. WHEN the load completes successfully, THE Importer SHALL report the tax year and the number of records loaded (77,988 for the tax year 2026 file).
18. IF the file at the path defined in App_Settings does not exist, cannot be read, cannot be decoded as windows-1255, or contains no record after the header row, THEN THE Importer SHALL fail, report the path and the reason, and leave the records in the Database unchanged.
19. IF the tax year of a row differs from the tax year being loaded (the tax year defined in App_Settings for the load at startup, or the tax year given to the manual load command), THEN THE Importer SHALL fail and report the row number, the tax year of the row and the tax year being loaded.
20. IF the automatic load that runs when Advisor_App starts fails, THEN THE Backend_API SHALL refuse to start accepting requests.

### Requirement 2: Usage Value Retrieval and Car Identification

**User Story:** As an employee, I want the bot to retrieve the usage value of my exact car from the official dataset, so that the comparison is based on official data and not on a guess.

#### Acceptance Criteria

1. WHEN Car_Lookup receives a complete Official_Key that exists in Usage_Value_Dataset, THE Car_Lookup SHALL return the Usage_Value of that record in ₪ exactly as stored in Usage_Value_Dataset, without recalculation or rounding.
2. WHEN Car_Lookup receives a complete Official_Key that exists in Usage_Value_Dataset, THE Car_Lookup SHALL return, together with the Usage_Value, the record's manufacturer, trade name, model description, list price, adjusted price and Powertrain.
3. IF the received Official_Key has no matching record in Usage_Value_Dataset, THEN THE Car_Lookup SHALL return an explicit "not found" result that contains no Usage_Value, without returning any other record (for example, a record that differs from the received Official_Key only in the registration year, the vehicle type code or the model code).
4. IF one or more of the five parts of the Official_Key (tax year, registration year, vehicle type code, manufacturer code, model code) is absent or empty after stripping leading and trailing whitespace, including the vehicle type code (without which the dataset has 512 collisions), THEN THE Car_Lookup SHALL reject the request without returning a record or a Usage_Value, and name every missing part.
5. WHEN Car_Lookup receives a registration year and a search text for a manufacturer or trade name, THE Car_Lookup SHALL return, from the tax year defined in App_Settings, all records of that registration year whose manufacturer name or trade name contains the search text after stripping the text's leading and trailing whitespace, ignoring the case of Latin letters (for example, "model 3" matches "MODEL 3"), and return each matching record once even when both the record's manufacturer name and trade name match.
6. WHEN Car_Lookup returns candidates from a search, THE Car_Lookup SHALL include for each candidate the Official_Key, manufacturer, trade name, model code, model description, vehicle type, engine displacement, Powertrain and list price.
7. WHEN the search matches more than one record, THE Car_Lookup SHALL return all candidates and indicate that a selection of a complete Official_Key is required.
8. IF the search matches no record, THEN THE Car_Lookup SHALL return an empty candidate list with an explicit indication that no candidates were found.
9. THE Advisor_Agent SHALL mark a car as identified only when the Employee has selected or confirmed a complete Official_Key, or when the car was chosen from Car_Catalog, so that a search that returns exactly one candidate leaves the car unidentified until the Employee confirms that candidate.
10. IF a car is known only by its manufacturer or trade name, without a complete Official_Key that the Employee selected or confirmed, THEN THE Advisor_Agent SHALL leave the car unidentified and present to the Employee, for selection, the candidates that the Car_Lookup search returned for the car's registration year and name.
11. WHEN Car_Lookup receives an Official_Key, THE Car_Lookup SHALL return a result (a record, a "not found" result or a rejection) within at most 100 milliseconds, measured from the moment Car_Lookup receives the request until Car_Lookup returns the result, using an indexed lookup against the full Usage_Value_Dataset (77,988 records for tax year 2026).
12. WHEN Car_Lookup receives a search request, THE Car_Lookup SHALL return the result (the candidates, an empty candidate list or a rejection) within at most 500 milliseconds, measured from the moment Car_Lookup receives the request until Car_Lookup returns the result, against the full Usage_Value_Dataset (77,988 records for tax year 2026).
13. IF a search request has no registration year, or the search text is empty or contains only whitespace, THEN THE Car_Lookup SHALL reject the request without returning candidates and state which input is missing.
14. IF Car_Lookup cannot read Usage_Value_Dataset from the Database (for example, because the Database is unavailable), THEN THE Car_Lookup SHALL return an explicit error result that is distinct from the "not found" result and from an empty candidate list, and that contains no Usage_Value and no candidates.

### Requirement 3: Rules Configuration File

**User Story:** As a developer who maintains the system, I want all challenge rules and payroll parameters to live in Rules_Config, so that updating a rule or an answer from Strauss changes the results without changing code.

#### Acceptance Criteria

1. THE Rules_Config SHALL define a monthly Car_Budget for each Eligibility_Group: A ₪3,500, B ₪3,700, C ₪4,500, D ₪5,200.
2. THE Rules_Config SHALL define the group order A < B < C < D, which determines which groups are lower than the employee's Eligibility_Group.
3. THE Rules_Config SHALL define the eligibility condition for Family_Track as a threshold of 4 children up to age 23, which an employee meets when the employee's number of children up to age 23 is equal to or greater than the threshold.
4. THE Rules_Config SHALL NOT define a Car_Cost for Family_Track, because the Car_Cost of a Family_Track car is the monthly cost of that car in Car_Catalog (₪6,000 for the Kia Carnival and ₪5,600 for the Hyundai Santa Fe in the challenge's catalog).
5. THE Rules_Config SHALL define the split of the gap between Car_Budget and Car_Cost in Family_Track as two percentages: 50% for the employer and 50% for the employee.
6. THE Rules_Config SHALL define the monthly EV_Refund amount, ₪250.
7. THE Rules_Config SHALL define the application mode of EV_Refund in a named field whose only values accepted by the schema are `net` (a net addition) and `taxable_gross` (a taxable gross addition, the challenge's simple alternative), with a default of `net`. With `net`, the Net_Pay of an electric Alternative rises by exactly the EV_Refund amount, which is the result that the challenge's grossed-up refund gives the employee; the gross amount that the employer pays is not calculated.
8. THE Rules_Config SHALL include the rule that Unused_Budget is not paid as salary as a named entry, whose only value accepted by the schema states that Unused_Budget is not paid, so that the rule cannot be switched off in Rules_Config.
9. THE Rules_Config SHALL include a flag that determines whether Participation reduces the taxable Usage_Value, with a default of `false`.
10. THE Rules_Config SHALL include a flag that determines whether commissions and bonuses are included in the pension and study fund contribution base, with a default of `true`, as in the challenge's net method.
11. THE Rules_Config SHALL include a flag that determines whether Car_Maintenance is a taxable payment outside the social benefits base (pension and study fund), with a default of `true`.
12. THE Rules_Config SHALL define the net pay calculation method in a named field whose only value accepted by the schema is `monthly`, so that any other value (such as `cumulative`) fails the schema validation in criterion 16.
13. THE Rules_Config SHALL define the payroll parameters of the challenge's rules file `mock-2026-10-12`, which are the 2025 tables that the challenge gives for illustration: income tax brackets at ₪7,010 10%, ₪10,060 14%, ₪16,150 20%, ₪22,440 31%, ₪46,690 35%, ₪60,130 47% and above that 50%; the tax credit point value ₪242; the National Insurance and health tax reduced and full rates, with the threshold ₪7,522 between them and the maximum insurable income ₪50,695; the pension credit of 35% on the employee's pension contribution up to 7% of an income ceiling of ₪9,500; and the study fund ceiling, the exempt employer rate and the rate of the employer's study fund deposit, which is 0, so that no employer deposit is added to the taxable income and the employee's study fund contribution only reduces Net_Pay.
14. THE Rules_Config SHALL attach to each group of payroll parameters listed in criterion 13 a non-empty reference to its source: the challenge's rules file for the parameters it defines, and a public source for the study fund ceiling and exempt rate, which that file does not have.
15. THE Rules_Config SHALL mark as pending, together with the default value in use and a description of the open question, each item that still awaits Strauss: the tax tables of the pilot year (marked on the tax credit point value) and the rate of the employer's study fund deposit. The schema SHALL accept any list of pending items, including an empty one, and SHALL require the default of each listed item to equal the current value of its field.
16. WHEN Backend_API starts, THE Backend_API SHALL validate Rules_Config, before accepting any request, against a schema that requires every item defined in criteria 1 to 14.
17. IF Rules_Config does not conform to the schema (a required item is missing, a value has the wrong type, or a value is not among the values the schema accepts), THEN THE Backend_API SHALL refuse to start, without accepting any request, and name each invalid field in the error message.
18. WHEN a value in Rules_Config changes and Backend_API is restarted, THE Backend_API SHALL use the new value in every calculation and eligibility decision made after the restart, without any code change.
19. THE Codebase SHALL read every rule value and every payroll parameter value defined in criteria 1 to 13 from Rules_Config only, so that no amount, percentage, threshold or group order from those criteria is hard-coded in any file other than Rules_Config, the sample Rules_Config file (criterion 20), test fixtures and expected test results.
20. THE Codebase SHALL include in Git a sample Rules_Config file that contains no secrets, passes the schema validation in criterion 16, and sets each item that has a default in criteria 7, 9, 10 and 11 to that default.
21. THE Advisor_App SHALL read secrets, such as the API key and the Database connection details, only from App_Settings.
22. IF the Rules_Config file is missing or cannot be parsed, THEN THE Backend_API SHALL refuse to start, without accepting any request, and state in the error message that the file is missing or the line at which parsing failed.
23. IF Rules_Config contains a negative monetary amount, a percentage outside the range 0% to 100%, Family_Track shares whose sum is not 100%, a Family_Track threshold that is not a whole number of 1 or more, a group order that does not contain each of A, B, C and D exactly once, or income tax brackets that are not in ascending order or that leave a gap or an overlap between consecutive brackets, THEN THE Backend_API SHALL treat Rules_Config as not conforming to the schema and refuse to start as defined in criterion 17.

### Requirement 4: Car Catalog and Occupations Table (Mock Data)

**User Story:** As a developer who maintains the system, I want a sample Car_Catalog and Occupations_Table that are based on real data and are replaced by Strauss's files without changing code, so that I can build and test the system before Strauss's data arrives.

#### Acceptance Criteria

1. THE Car_Catalog SHALL hold the 20 cars of the challenge's catalog sheet: 18 cars in the Eligibility_Group values A-D and 2 Family_Track cars (the sheet's text says "20 plus 2", but its rows are 20 in all), each built from a real record in Usage_Value_Dataset, so that the car's Official_Key identifies that record. The two Family_Track cars, which the sheet puts in a group of their own, are stored in group A, so that the group filter shows them to every employee and the number of children decides who may take them.
2. THE Car_Catalog SHALL include for each car the complete Official_Key (tax year, registration year, vehicle type code, manufacturer code and model code), a non-empty display name, the registration year, the monthly Car_Cost to the company in ₪ and the Eligibility_Group (one of A, B, C or D), and SHALL accept for each car two optional fields: `default_participation`, the Default_Participation, a monthly amount in ₪ of ₪0 or more, and `usage_value`, the usage value that the sheet lists, a whole amount in ₪ of ₪0 or more, used only as a check value (criteria 18-19). The shipped file SHALL set both fields for all 20 cars, from the sheet.
3. THE Car_Catalog SHALL include at least one car from each of the four Eligibility_Group values (A, B, C and D).
4. THE Car_Catalog SHALL include at least 3 cars whose Powertrain, according to the car's record in Usage_Value_Dataset, is electric.
5. THE Car_Catalog SHALL include at least one car marked as a Family_Track car.
6. WHEN Backend_API starts, THE Backend_API SHALL verify, before serving any request, that the Official_Key of every car in Car_Catalog identifies a record in Usage_Value_Dataset.
7. IF one or more cars in Car_Catalog are not found in Usage_Value_Dataset by Official_Key, THEN THE Backend_API SHALL refuse to start and list in the error message every car that was not found, each identified by the car's display name and complete Official_Key, not only the first car that was not found.
8. WHEN the Car_Catalog list is requested for an Employee, THE Backend_API SHALL return only cars from the employee's Eligibility_Group (the group of the employee's occupation, or the Group_Override) and from the groups lower than it according to the order in Rules_Config (for example: an employee in group C receives cars from A, B and C, and not from D).
9. WHEN Backend_API returns a list of cars from Car_Catalog, THE Backend_API SHALL label each car in the list with the car's Eligibility_Group.
10. THE Occupations_Table SHALL hold the 14 occupations of the challenge's occupations sheet, each with the occupation name exactly as the sheet writes it, the occupation's Eligibility_Group (one of A, B, C or D), whether the car is mandatory in that occupation (yes or no), whether giving up the car is allowed in that occupation (yes or no), and the monthly Car_Maintenance amount in ₪, which is ₪0 for an occupation in which giving up the car is not allowed.
11. THE Occupations_Table SHALL include at least one occupation in which giving up the car is allowed and at least one occupation in which the car is mandatory.
12. WHEN Car_Catalog or Occupations_Table is replaced with a Strauss file that has the same fields and file format as the Mock_Data file it replaces, and Backend_API is restarted, THE Backend_API SHALL use the data from the new file without any code change, including when the new file contains a different number of cars or occupations than the Mock_Data file.
13. THE Codebase SHALL include within each of the Car_Catalog and Occupations_Table files themselves an explicit marker stating that the file contains Mock_Data that is to be replaced by Strauss's file.
14. THE Explanations_File SHALL include a request to Strauss to add the vehicle type code to each car in Strauss's catalog, together with the reason: the catalog's fields (model, manufacturer code, model code, registration year, monthly cost and group) do not include the vehicle type code, and without the vehicle type code the Official_Key is incomplete. Every car of the challenge's catalog matches the dataset with vehicle type code 1.
15. IF a car in Car_Catalog is missing one of the required fields listed in criterion 2, has an Eligibility_Group that is not one of A, B, C or D, has a Car_Cost that is not an amount greater than ₪0, or has a `default_participation` or `usage_value` lower than ₪0, THEN THE Backend_API SHALL refuse to start and list in the error message every invalid car together with each missing or invalid field.
16. IF a record in Occupations_Table is missing one of the fields listed in criterion 10, has an Eligibility_Group that is not one of A, B, C or D, has a Car_Maintenance amount lower than ₪0, is marked both as an occupation in which the car is mandatory and as one in which giving up the car is allowed, or has the same occupation name as another record, THEN THE Backend_API SHALL refuse to start and list in the error message every invalid record together with each missing, invalid, contradictory or duplicated field.
17. IF the Car_Catalog list is requested for an Employee whose Eligibility_Group is unknown, because the occupation is missing from Employee_Profile or matches no Occupations_Table entry and there is no Group_Override, THEN THE Backend_API SHALL return an empty list of cars with an explicit indication of the missing field "occupation", instead of cars from any Eligibility_Group.
18. WHEN Backend_API starts, THE Backend_API SHALL compare the `usage_value` of every car in Car_Catalog that has one with the Usage_Value of the car's record in Usage_Value_Dataset, and SHALL use only the Usage_Value of Usage_Value_Dataset in every calculation.
19. IF the `usage_value` of one or more cars in Car_Catalog differs from the Usage_Value of the car's record in Usage_Value_Dataset, THEN THE Backend_API SHALL start all the same, write one warning line to the log for each such car, with the car's display name, Official_Key and both amounts, and list each such car with both amounts in the response of the health route (Requirement 14, criterion 9), without changing the health status, so that a wrong model code in Strauss's catalog is found and not silently used.

### Requirement 5: Eligibility Check

**User Story:** As an employee, I want to know for each alternative whether I am eligible for it and why, according to Strauss's rules, so that I do not count on an alternative that is not allowed and do not receive an eligibility that the bot made up.

#### Acceptance Criteria

1. THE Eligibility_Checker SHALL return for each Alternative exactly one of three statuses, `eligible`, `not_eligible` or `missing`, together with a non-empty reason in Hebrew and a list of missing fields, which is empty for the statuses `eligible` and `not_eligible`.
2. WHEN Eligibility_Checker returns the status `eligible` or `not_eligible`, THE Eligibility_Checker SHALL include in the reason the rule that was applied and the values on which the decision was based: for a car in the regular track, the car's Eligibility_Group and the employee's Eligibility_Group; for a Family_Track car, the number of children up to age 23 and the threshold in Rules_Config; and for giving up the car, the occupation and whether Occupations_Table allows giving up the car in that occupation (for example: "A car from group C is allowed for an employee in group D").
3. THE Eligibility_Checker SHALL compute the result only from the inputs passed to the Eligibility_Checker (Employee_Profile, Alternative, Rules_Config, Car_Catalog, Occupations_Table and the car's Usage_Value_Dataset record), without modifying those inputs and without accessing the Database, the network or the language model.
4. WHEN Eligibility_Checker is invoked multiple times with the same inputs, THE Eligibility_Checker SHALL return on every invocation the same status, the same reason and the same list of missing fields.
5. WHEN the Alternative is a car in the regular track (a car in Car_Catalog that is not marked as a Family_Track car) and the car's Eligibility_Group in Car_Catalog is equal to or lower than the employee's Eligibility_Group according to the order in Rules_Config, THE Eligibility_Checker SHALL return the status `eligible` (for example: an employee in group D who chooses a car from group C, or an employee in group C who chooses a car from group C).
6. ### Requirement 7: Monthly Net Pay Calculation

**User Story:** As an employee, I want my monthly net pay in each alternative to be calculated in code according to the challenge's net method and its payroll tables (the 2025 tables, per the challenge), with a breakdown of every component, so that I can trust the difference and check the difference against my payslip.

#### Acceptance Criteria

1. THE Payroll_Calculator SHALL calculate Net_Pay in code only, using only its inputs and Rules_Config, without invoking the language model, without accessing the Database or the network and without modifying its inputs, and return the same status, the same Net_Pay and the same breakdown on every run with the same input and the same Rules_Config.
2. THE Payroll_Calculator SHALL receive as input, with every amount in ₪ per month: base salary, commissions and bonuses (each component separately), the employee's pension contribution percentage, the employee's study fund contribution percentage and tax credit points, and, from the scenario being examined: Usage_Value (₪0 when giving up the car or without a car), Participation (₪0 when giving up the car or without a car), EV_Refund (₪0 when the scenario's car is not electric or there is no car) and Car_Maintenance (₪0 when the scenario has a car, and the amount of the employee's occupation in Occupations_Table when the scenario has no car, which is both giving up the car and a Today without a car, Requirement 8, criterion 2).
3. IF one or more of the input fields in criterion 2 was not provided (for example: tax credit points), where a field provided as ₪0 or 0 (for example: no commissions) counts as provided, THEN THE Payroll_Calculator SHALL return the status `missing` with the list of all the missing fields, without a Net_Pay and without a breakdown, instead of a Net_Pay calculated from a default value.
4. THE Payroll_Calculator SHALL calculate the gross salary as the base salary plus the sum of all commission components, the sum of all bonus components and Car_Maintenance, plus EV_Refund only as defined in criterion 5, without adding Usage_Value or Participation.
5. WHERE the EV_Refund application mode in Rules_Config is `taxable_gross`, THE Payroll_Calculator SHALL add EV_Refund to the gross salary before the tax calculation, so that EV_Refund is part of the taxable income on which income tax, National Insurance and health tax are calculated.
6. THE Payroll_Calculator SHALL calculate the taxable income as the gross salary plus the taxable Usage_Value (according to the Participation flag in Requirement 6, criteria 15-16), plus every additional taxable component defined in the payroll parameters in Rules_Config (the employer's study fund deposit above the ceiling, which is ₪0 while the rate of that deposit is 0, Requirement 3, criterion 13), with no other additions and no deductions.
7. THE Payroll_Calculator SHALL calculate the income tax before credits using the monthly method, by applying each income tax bracket rate in Rules_Config only to the part of the month's taxable income that falls within that bracket and summing the results.
8. THE Payroll_Calculator SHALL calculate the credits as the tax credit points multiplied by the tax credit point value, plus the pension credit (the credit rate multiplied by the employee's pension contribution that qualifies for the credit, up to the ceiling), according to Rules_Config, and calculate the income tax as the income tax before credits minus the credits, or ₪0 when the credits exceed the income tax before credits, without applying the excess credit to any other component.
9. THE Payroll_Calculator SHALL calculate National Insurance and health tax separately, on the taxable income including Usage_Value, each at its own reduced rate in Rules_Config on the part up to the income threshold, at its own full rate in Rules_Config on the part between the income threshold and the maximum insurable income, and at ₪0 on the part above the maximum insurable income.
10. THE Payroll_Calculator SHALL calculate the employee's pension contribution and study fund contribution as the corresponding percentage multiplied by a contribution base made of the base salary, plus the commissions and the bonuses only when the flag of Requirement 3, criterion 10 is on (`true`, the default), plus Car_Maintenance only when the Car_Maintenance flag in Rules_Config is off (`false`), and never including Usage_Value, Participation or EV_Refund.
11. THE Payroll_Calculator SHALL calculate Net_Pay as the gross salary minus income tax, National Insurance, health tax, the employee's pension contribution, the employee's study fund contribution and Participation, plus EV_Refund only when the EV_Refund application mode in Rules_Config is `net`, without adding Usage_Value to Net_Pay.
12. THE Payroll_Calculator SHALL calculate with exact decimal arithmetic without rounding in intermediate steps and return Net_Pay and every breakdown amount unrounded, so that amounts are rounded to whole shekels only when displayed, with the same rounding rule for all displayed amounts: half away from zero (for example: ₪1,234.50 is displayed as ₪1,235, ₪1,234.49 as ₪1,234 and −₪0.50 as −₪1).
13. WHEN Payroll_Calculator calculates a Net_Pay, THE Payroll_Calculator SHALL return together with the Net_Pay a breakdown of every component: gross salary, taxable Usage_Value, taxable income, tax before credits, credits (the tax credit points credit and the pension credit, each separately, as calculated in criterion 8 before the income tax is limited to ₪0), income tax, National Insurance, health tax, employee pension contribution, employee study fund contribution, Participation, EV_Refund, Car_Maintenance and Net_Pay.
14. THE Explanations_File SHALL document that the Payroll_Calculator implements only the monthly method, that the cumulative method was not implemented because the cumulative method requires salary data from the beginning of the year, and that locality-based tax benefits are out of scope and are a known limitation of the calculation.
15. THE Codebase SHALL include the six sample employees of the challenge (E-001 to E-006) as golden tests, with the reference values of the challenge's calculation sheet, and allow adding Strauss's approved sample employees by adding data only, without any code change. For each employee, Payroll_Calculator and Comparison_Engine, run with the shipped Rules_Config, Car_Catalog and Occupations_Table, with the Default_Participation of the new car, SHALL return a Net_Pay of Today, a Net_Pay of the Alternative and a difference that equal the reference values after rounding to whole shekels by the rule in criterion 12; for Today, and for the Alternatives without an EV_Refund, the income tax and the National Insurance plus health tax SHALL equal the reference values as well (the sheet's figures for an electric Alternative include the grossed-up refund, which the `net` mode does not calculate).
16. IF an input amount in criterion 2 (base salary, a commission or bonus component, Usage_Value, Participation, EV_Refund or Car_Maintenance) is negative, the employee's pension or study fund contribution percentage is below 0% or above 100%, or the tax credit points are negative, THEN THE Payroll_Calculator SHALL return an error that lists all the invalid fields with the value received for each, without a Net_Pay and without a breakdown.

### Requirement 8: Comparison Engine and Explanation

**User Story:** As an employee, I want to see for each alternative, against my current situation, the estimated net pay, the difference and what caused the difference, with a short explanation in plain words, so that I understand what each choice does to my net pay and can check the numbers.

#### Acceptance Criteria

1. THE Comparison_Engine SHALL receive as input Employee_Profile and a list of one or more Alternative items, each of which is another car from Car_Catalog (including a car whose Powertrain is electric), a car in Family_Track, or giving up the car.
2. THE Comparison_Engine SHALL calculate Today once per invocation of Comparison_Engine, with the current car and the Participation in the current car according to Employee_Profile, or without a car for an employee whose Employee_Profile records no current car, as the single baseline for the difference of every Alternative in that invocation, and return for Today the car (or "no car"), Participation, Usage_Value, EV_Refund or Car_Maintenance, and Net_Pay. An employee with no car has given it up, so Today without a car takes as its Car_Maintenance the amount of the employee's occupation in Occupations_Table (the challenge's employee E-003).
3. THE Comparison_Engine SHALL calculate every Alternative with the same Employee_Profile data that was used to calculate Today, so that the inputs passed to Payroll_Calculator for an Alternative differ from the inputs passed to Payroll_Calculator for Today only in the car-related components: Usage_Value, Participation, EV_Refund and Car_Maintenance.
4. THE Comparison_Engine SHALL obtain the eligibility decision and the reason from Eligibility_Checker according to Requirement 5, the Participation, the Family_Track split and Unused_Budget according to Requirement 6, and Net_Pay and the breakdown of the Net_Pay components from Payroll_Calculator according to Requirement 7, without implementing those rules a second time.
5. THE Comparison_Engine SHALL return for each Alternative exactly the items of the challenge's "What to submit" section, in this order: the car, or "giving up the car"; whether the employee is eligible and why, as returned by Eligibility_Checker; Car_Cost and Car_Budget; the employee's Participation with its source (Requirement 6, criterion 25), and in Family_Track also the employee's share and the employer's share of the gap; Usage_Value; EV_Refund or Car_Maintenance; the estimated Net_Pay; the difference from Today (the Net_Pay of the Alternative minus the Net_Pay of Today) with a breakdown of what changed; and the Explanation.
6. THE Comparison_Engine SHALL break down the difference from Today into four components, in this order: Usage_Value (which affects Net_Pay only through income tax, National Insurance and health tax), EV_Refund, Participation and Car_Maintenance, where each component is the change in Net_Pay, including the effect on all deductions, that results from changing that item from its Today value to its Alternative value, with the items earlier in the order already set to their Alternative values and the items later in the order still at their Today values.
7. THE Comparison_Engine SHALL return breakdown components whose sum equals the difference from Today exactly, both in the exact amounts and in the amounts rounded to whole shekels that are displayed to the employee (Requirement 7, criterion 12), so that the displayed difference equals the displayed Net_Pay of the Alternative minus the displayed Net_Pay of Today, the displayed breakdown components add up to the displayed difference, and each displayed breakdown component differs from the component's exact amount by less than ₪1.
8. THE Comparison_Engine SHALL calculate the comparison and build the Explanation in code only, without invoking the language model, and return identical output, including the Explanation text, on every run with the same input and the same Rules_Config, Car_Catalog, Occupations_Table and Usage_Value_Dataset.
9. THE Comparison_Engine SHALL build the Explanation from fixed templates in plain Hebrew, without code identifiers, status values or formulas, that are filled in from the displayed difference and the displayed breakdown components (criterion 7): first the direction of the change in net pay (up for a displayed difference greater than ₪0, down for a displayed difference less than ₪0, unchanged for a displayed difference of ₪0) and the monthly size of the change as the absolute value of the displayed difference, and then, in the order of criterion 6, every breakdown component whose displayed amount is other than ₪0, with the component's amount in absolute value and wording that states whether the component raises or lowers Net_Pay, in up to two lines of up to 120 characters each, including for an Alternative in which all four breakdown components are other than ₪0. For example (UI copy is Hebrew): "Net pay goes up by ₪210 a month: the lower usage value saves ₪310, an EV refund of ₪250 is added, and a participation of ₪350 is deducted."
10. THE Comparison_Engine SHALL include in the Explanation only amounts that are identical, in absolute value, to the rounded amounts of the difference and of the breakdown components of the same Alternative, as displayed in the comparison table.
11. IF Eligibility_Checker returns the status `not_eligible` for an Alternative, THEN THE Comparison_Engine SHALL return for that Alternative the car, or "giving up the car", the status `not_eligible` and the reason from Eligibility_Checker, without Net_Pay, a difference from Today, a breakdown or an Explanation, including for an Alternative for which information required to calculate Net_Pay is missing.
12. IF Eligibility_Checker returns the status `missing` for an Alternative, or Eligibility_Checker returns the status `eligible` and information required to calculate the Net_Pay of that Alternative is missing (for example: the Participation in a new car that has no Default_Participation and no answer of Transport_Rep), THEN THE Comparison_Engine SHALL return that Alternative with the status `pending`, with the items of criterion 5 that are already known, the list of all the missing fields, with each field listed once (Requirement 5, criterion 21; Requirement 6, criteria 5 and 10; Requirement 7, criterion 3) and, for each missing field, whether a Rep_Question about that field was sent to Transport_Rep, without Net_Pay, a difference from Today, a breakdown or an Explanation.
13. IF one or more Alternative items have the status `not_eligible` or `pending`, THEN THE Comparison_Engine SHALL continue to calculate Today and the remaining Alternative items, and return Today and every remaining Alternative with the same values as in a comparison of the same input without the Alternative items that have the status `not_eligible` or `pending`.
14. IF information required to calculate the Net_Pay of Today is missing, THEN THE Comparison_Engine SHALL return Today with the status `pending` and the list of all the missing fields, return every Alternative that does not have the status `not_eligible` with the status `pending` and with the missing fields of Today included in the Alternative's list of missing fields (for example: "participation in the current car", Requirement 6, criterion 5), and return every Alternative without a difference from Today, a breakdown or an Explanation.
15. WHEN Employee_Profile is updated, Transport_Rep answers a Rep_Question, or the Employee chooses a different car for an Alternative in Employee_Screen, THE Advisor_App SHALL recalculate Today and every Alternative in the Employee's current comparison using Comparison_Engine, without invoking the language model.
16. IF Employee_Profile records no current car and the occupation is missing from Employee_Profile or matches no Occupations_Table entry, THEN THE Comparison_Engine SHALL return Today with the status `pending` and the missing field "occupation", and every Alternative that is not `not_eligible` with the status `pending` and the same missing field.
17. IF Employee_Profile records no current car and the employee's occupation is one in which the car is mandatory, THEN THE Comparison_Engine SHALL return Today with the status `pending` and the missing field "current car", without calculating a Today without a car, because that situation cannot exist; and THE Advisor_Agent SHALL tell the Employee that the occupation comes with a company car and ask which car the Employee has.

IF information required for an eligibility check or for a calculation is missing, THEN THE Advisor_Agent SHALL ask the Employee for the information, or, when the Employee cannot provide the information, meaning that the Employee replies that the Employee does not know the information or that the information is provided only by Transport_Rep (for example: the Participation in a new car that Car_Catalog does not list, Requirement 6, criterion 24, or an occupation that is not in Occupations_Table, Requirement 5, criterion 16), send a Rep_Question, write to the Employee in the wording "I'm missing X, I asked the representative" (UI copy is Hebrew), with the name of the missing field in place of X, and display the interim comparison from Comparison_Engine (Requirement 8, criterion 12), without guessing a value for the missing field.
7. THE Advisor_Agent SHALL tell the Employee whether an Alternative is allowed, and what the reason is, only with the status and the reason that Eligibility_Checker (Requirement 5) returned for that Alternative, without stating a decision for an Alternative before Eligibility_Checker has returned a result for that Alternative, and handle a result with the status `missing` according to criterion 6.
8. WHEN the Employee describes a car that is not from Car_Catalog, such as the current car, THE Advisor_Agent SHALL identify the car according to Requirement 2: display the candidates from Car_Lookup with the details that distinguish between the candidates and ask the Employee to choose, ask for the model code from the vehicle license, or send a Rep_Question.
9. WHEN the Employee asks to examine giving up the car, for example an employee from group B, THE Advisor_Agent SHALL ask about the occupation if the occupation is missing in Employee_Profile, check giving up the car with Eligibility_Checker, and display the decision, Car_Maintenance and the comparison as Comparison_Engine returned them.
10. THE Advisor_Agent SHALL write every response in Hebrew, in a neutral tone with no exclamation marks, in the combined feminine/masculine "you" form (UI copy is Hebrew) when grammatical gender is required, and without emoji.
11. WHEN the Employee sends a message, THE Advisor_App SHALL display in Employee_Screen the response of Advisor_Agent as one complete message, without streaming of partial text, within at most 8 seconds, measured from the moment the Employee sends the message until the complete response is displayed, in 90% of the turns in the challenge script.
12. THE Advisor_Agent SHALL complete the challenge script, from the Employee's first message until the full comparison is displayed, within a cumulative response time of at most 60 seconds, calculated as the sum of the response times of all turns measured as in criterion 11, excluding the Employee's typing time and the time spent waiting for an answer from Transport_Rep.
13. IF the Employee asks a question that is not about the company car or the net pay, THEN THE Advisor_Agent SHALL reply, in the tone defined in criterion 10 and without answering the question, that Advisor_Agent helps only with questions about the company car and the net pay.
14. THE Advisor_Agent SHALL use the language model provider and the model defined in App_Settings, and use OpenAI when App_Settings does not define a provider.
15. IF the language model's API key is missing in App_Settings or is rejected by the language model provider as invalid, THEN THE Advisor_App SHALL display in Employee_Screen, no later than in place of the response to the Employee's next message, an error message in Hebrew that Advisor_Agent is unavailable because the API key in App_Settings is missing or invalid, keep the Employee's message in the Conversation, and continue to display the comparison table and to recalculate the comparison according to Requirement 8, criterion 15.
16. IF a value that the Employee provides in a message is invalid according to Requirement 11, criterion 3 (a negative amount, a percentage outside the range 0-100 or a negative number of tax credit points), THEN THE Advisor_App SHALL leave the stored value of that field in Employee_Profile unchanged, save the other valid fields of the same message according to criterion 2, and have Advisor_Agent ask the Employee again, in Hebrew, for that field together with the allowed range.
17. IF an Agent_Tool returns an error instead of a result, THEN THE Advisor_Agent SHALL tell the Employee, in Hebrew, which action failed (for example: the car search or the comparison calculation), without presenting for that action any number, eligibility decision or car identification that the Agent_Tool did not return.
18. IF the language model returns an error other than a missing or invalid API key, or Advisor_Agent does not complete a response within 60 seconds of the Employee sending a message, THEN THE Advisor_App SHALL keep the Employee's message in the Conversation and the fields already saved to Employee_Profile, display in Employee_Screen a message in Hebrew that the bot did not answer and that the Employee can send the message again, and continue to display the comparison table and to recalculate the comparison according to Requirement 8, criterion 15.
19. THE Advisor_Agent SHALL have the occupation names of Occupations_Table in its instructions, SHALL save the occupation under the name of the table when the Employee's words clearly name one of its entries, also in the other gender, and SHALL show the list and ask which entry is the Employee's when the words fit several entries or none; only when the Employee says that none of the entries is the Employee's SHALL it save the Employee's own words and send the Rep_Question of Requirement 5, criterion 16.
20. THE Advisor_Agent SHALL never ask the Employee for the Eligibility_Group and SHALL never save a group that the Employee states. IF the Employee states an Eligibility_Group that differs from the employee's Eligibility_Group (Requirement 5, criterion 23), THEN THE Advisor_Agent SHALL tell the Employee that the group follows from the occupation, name the group that is in use, and offer to ask Transport_Rep; WHEN the Employee accepts, THE Advisor_Agent SHALL send a Rep_Question of the eligibility group type (Requirement 10, criterion 17).

### Requirement 10: Question to the Representative and Resuming from the Same Point

**User Story:** As an employee, I want the bot, when information that only the transport representative can provide is missing, to ask the representative, and my conversation to resume from the same point when the representative answers, so that I get a full comparison without emails and without starting the conversation over.

#### Acceptance Criteria

1. WHEN Advisor_Agent finds that a field required for an eligibility check or a calculation is missing and only Transport_Rep can provide the field, such as the Participation in a new car that Car_Catalog does not list (Requirement 6, criterion 24) or the entry of Occupations_Table for an occupation that does not appear in it (Requirement 5, criterion 16), or the Employee asks for the confirmation of Transport_Rep (Requirement 6, criterion 23; Requirement 9, criterion 20), THE Advisor_Agent SHALL create one Rep_Question for each such missing field and relevant car using the Agent_Tool for sending a Rep_Question.
2. WHEN Advisor_Agent creates a Rep_Question, THE Advisor_App SHALL store the Rep_Question in the Database with the question type, the question text, the creation time, the Employee's display name, Eligibility_Group, the relevant car, when there is such a car, by display name and Official_Key, the Conversation ID, the missing field and the status `open`.
3. WHEN Advisor_Agent creates a Rep_Question, or receives an existing Rep_Question according to criterion 4, THE Advisor_Agent SHALL, in the same response, notify the Employee in the wording "I'm missing X, I asked the representative" (UI copy is Hebrew), with the name of the missing field in place of X, and display the interim comparison in which the Alternative has the status `pending` and the missing field is marked as sent to Transport_Rep, as defined in Requirement 9, criterion 6 and in Requirement 8, criterion 12.
4. IF Advisor_Agent requests a Rep_Question while an open Rep_Question already exists for the same Conversation, the same missing field and the same relevant car (or, for a Rep_Question without a relevant car, the same Conversation and the same missing field), including two requests made concurrently, THEN THE Advisor_App SHALL return the existing open Rep_Question to Advisor_Agent instead of creating an additional Rep_Question, so that the Database holds exactly one open Rep_Question for that combination.
5. THE Advisor_App SHALL accept an answer to a Rep_Question of the Participation type only as a structured answer with an amount in ₪ of 0 or more, a required effective date and an optional note, as defined in Requirement 6, criteria 17-18 and Requirement 12, criterion 6, and reject any other answer to that type according to Requirement 12, criterion 7.
6. THE Advisor_App SHALL accept an answer to a Rep_Question of the occupation type only as the name of one entry of Occupations_Table, an answer to a Rep_Question of the eligibility group type only as one of A, B, C or D, and an answer to a Rep_Question of the other type as free text that contains at least one character other than a space, and reject any other answer according to Requirement 12, criterion 7.
7. WHEN Transport_Rep submits a valid answer according to criteria 5-6 to a Rep_Question with the status `open`, THE Advisor_App SHALL store the answer in the Database and mark the Rep_Question with the status `answered` before the resumption of the Conversation according to criterion 10 starts.
8. IF Transport_Rep submits an answer to a Rep_Question that has already been answered, including a second answer submitted concurrently with the first, THEN THE Advisor_App SHALL reject the answer, leave the stored answer unchanged, not resume the Conversation a second time, and display in Rep_Screen a message in Hebrew that the question has already been answered.
9. WHILE a Rep_Question has the status `answered`, THE Advisor_App SHALL display the Rep_Question and the stored answer as read-only, without an answer form and without any control that changes the answer.
10. WHEN a Rep_Question is marked `answered`, THE Backend_API SHALL resume the same Conversation on the server side from the point at which the Conversation stopped, without any action by the Employee, by passing the answer to Advisor_Agent together with the stored message history of the Conversation, so that the Conversation keeps the same Conversation ID, the new messages are added after the last stored message, and no message that was already stored is removed or repeated.
11. WHEN Advisor_Agent receives an answer to a Rep_Question, THE Advisor_Agent SHALL add to the Conversation one message in Hebrew that names the field that Transport_Rep answered and presents the updated comparison that Advisor_App recalculated according to Requirement 8, criterion 15, in which an answer of the Participation type is used as the Participation of the Alternative with the relevant car of the Rep_Question.
12. WHILE the Conversation has at least one open Rep_Question or a resumption of the Conversation according to criterion 10 is in progress, THE Employee_Screen SHALL check Backend_API for updates (polling) at least once every 5 seconds, and display a new message and the updated comparison at the first check after the message is stored, without a manual page refresh.
13. WHILE the Conversation has no open Rep_Question and no resumption of the Conversation according to criterion 10 is in progress, THE Employee_Screen SHALL not check Backend_API for updates (polling).
14. THE Advisor_App SHALL store the Rep_Question items, the answers and the Conversation in the Database, so that after a page refresh or a restart of Backend_API the Rep_Question items with their status, the answers and the Conversation messages are displayed unchanged, and an answer to a Rep_Question that remained open across the restart resumes the Conversation according to criterion 10.
15. IF resuming the Conversation fails after an answer from Transport_Rep, for example due to a language model error or a missing or invalid API key (Requirement 9, criterion 15), THEN THE Advisor_App SHALL keep the answer stored and the Rep_Question with the status `answered`, keep the stored message history of the Conversation as it was before the resumption, recalculate the comparison according to Requirement 8, criterion 15, and display in Employee_Screen a message in Hebrew that the answer was received and the comparison was updated, but the bot could not continue the conversation.
16. IF the Agent_Tool for sending a Rep_Question fails to store the Rep_Question in the Database, THEN THE Advisor_Agent SHALL tell the Employee in Hebrew that the question could not be sent to Transport_Rep, instead of the wording in criterion 3, and display the interim comparison in which the missing field is marked as not sent to Transport_Rep (Requirement 8, criterion 12).
17. WHEN Transport_Rep answers a Rep_Question of the occupation type, THE Advisor_App SHALL store the chosen entry's name as the occupation in Employee_Profile, and WHEN Transport_Rep answers a Rep_Question of the eligibility group type, THE Advisor_App SHALL store the chosen group as the Group_Override in Employee_Profile, in both cases in the same transaction as the answer and before the comparison is recalculated (Requirement 8, criterion 15), so that the Eligibility_Group, the eligibility decisions and the Car_Maintenance follow the answer without an action of Advisor_Agent.

### Requirement 11: Employee Screen (Employee_Screen)

**User Story:** As an employee, I want one screen where I chat with the bot, see and correct my data and compare the alternatives, so that I can check every change and immediately see the effect on the net pay, even without waiting for the bot.

#### Acceptance Criteria

1. THE Employee_Screen SHALL display the conversation with Advisor_Agent, the My Details panel and the comparison table on the same screen, without navigating to another page, and, at viewport widths of 1024 pixels or more (Requirement 16, criterion 8), keep the My Details panel visible while the Employee scrolls the conversation and when new messages are added.
2. THE Employee_Screen SHALL display in the My Details panel every Employee_Profile field that has a stored value, with the value stored in the Database, and allow editing the value of every displayed field directly in the My Details panel, without sending a message to Advisor_Agent, except the Eligibility_Group, which the panel SHALL display as read-only together with its source (the occupation, or Transport_Rep for a Group_Override), or as unknown until the occupation matches an entry of Occupations_Table.
3. IF the Employee enters an invalid value in the My Details panel: a negative amount, a percentage outside the range 0-100, a negative number of tax credit points, a number of children up to age 23 that is negative or not a whole number, or a non-numeric value in a numeric field, THEN THE Advisor_App SHALL reject the value, leave the stored value in Employee_Profile unchanged, not recalculate the comparison, and display next to the field an error message in Hebrew with the allowed values or range.
4. WHEN the Employee corrects a field in the My Details panel, by leaving the edited field or pressing Enter, or in the conversation (Requirement 9, criterion 2), THE Advisor_App SHALL update the same Employee_Profile in the Database, display the updated value in the My Details panel and recalculate the comparison according to Requirement 8, criterion 15, displaying the updated comparison table within at most 2 seconds of a correction in the My Details panel, or together with the response of Advisor_Agent for a correction in the conversation, so that Advisor_Agent uses the updated value in the next turn without asking for that field again.
5. THE Employee_Screen SHALL display the comparison table with a "Today" column, showing the items that Comparison_Engine returns for Today (Requirement 8, criterion 2), and a column for each Alternative that was examined in the Conversation, and with a row for each item of the "What to submit" section in the order of Requirement 8, criterion 5, displaying every value exactly as Comparison_Engine returned it, with amounts rounded to whole shekels (Requirement 7, criterion 12).
6. WHILE an Alternative is waiting for missing information, with the status `pending` (Requirement 8, criterion 12, which also covers the Eligibility_Checker status `missing`), or is not allowed according to Eligibility_Checker, with the status `not_eligible` (Requirement 8, criterion 11), THE Employee_Screen SHALL display in the column of the Alternative the status and the reason, and, for the status `pending`, also the items that are already known, the list of all the missing fields (Requirement 5, criterion 21) and, for each missing field, whether a Rep_Question was sent to Transport_Rep, and display no Net_Pay, difference from Today, breakdown or Explanation in that column.
7. THE Employee_Screen SHALL allow replacing the car in the column of an Alternative that includes a car, using a picker from Car_Catalog that displays only cars from the Employee's Eligibility_Group and from the groups below that group (Requirement 4, criterion 8), with the display name and the Eligibility_Group of each car (Requirement 4, criterion 9).
8. WHEN the Employee chooses a different car in the picker, THE Employee_Screen SHALL request from the calculation API in Backend_API, without invoking the language model (Requirement 8, criterion 15), to store the chosen car in that Alternative of the Conversation and to recalculate the comparison, and display the updated table, including the eligibility status of the chosen car, within at most 2 seconds of the choice.
9. WHEN the Employee opens Employee_Screen without a Conversation ID in the URL, THE Advisor_App SHALL create a new Conversation with no messages and with an empty Employee_Profile, and add the ID of the new Conversation to the URL.
10. WHEN the Employee refreshes Employee_Screen or reopens a URL with the ID of an existing Conversation, THE Employee_Screen SHALL load, through Backend_API, from the Database the messages, Employee_Profile, the Alternative items and the last stored comparison of that Conversation, display the messages in their original order, the stored values in the My Details panel and the stored comparison in the comparison table, and continue the conversation from the same point, so that Advisor_Agent answers the next message using the stored message history without asking again about a field stored in Employee_Profile (Requirement 9, criterion 1).
11. IF the URL contains a Conversation ID that does not exist in the Database, including an ID in an invalid format, THEN THE Employee_Screen SHALL display a message in Hebrew that the conversation was not found and an action to open a new conversation according to criterion 12, without creating a Conversation until the Employee selects that action.
12. WHEN the Employee selects the "New conversation" action, THE Advisor_App SHALL create a new Conversation with no messages and with an empty Employee_Profile, display the new ID in the URL, display an empty conversation and an empty My Details panel, and keep the previous Conversation stored in the Database, so that opening the URL of the previous Conversation loads it according to criterion 10.
13. WHILE Employee_Screen is waiting for a response from Advisor_Agent, from the moment the Employee sends a message until the response of Advisor_Agent or an error message is displayed, THE Employee_Screen SHALL display a typing indicator.
14. WHEN Employee_Screen displays a new message from Advisor_Agent, THE Employee_Screen SHALL announce the full text of the message to screen readers once, through an aria-live region, without moving the keyboard focus.
15. IF Advisor_Agent cannot respond, because the API key is missing or invalid (Requirement 9, criterion 15) or because the language model returns an error, THEN THE Employee_Screen SHALL remove the typing indicator, display a message in Hebrew that Advisor_Agent is unavailable, keep the messages already displayed, and continue to allow editing in the My Details panel, replacing a car in the comparison table and recalculation according to criteria 4 and 8.
16. WHILE Today has the status `pending` in the latest comparison (Requirement 8, criterion 14), THE Employee_Screen SHALL display in the "Today" column the status and the list of all the missing fields, and display in every Alternative column no difference from Today, breakdown or Explanation.
17. IF Backend_API returns an error or cannot be reached when the Employee saves a field in the My Details panel or chooses a car in the picker, THEN THE Advisor_App SHALL leave Employee_Profile and the Alternative items in the Database unchanged, and display in Employee_Screen an error message in Hebrew that the change was not saved, with the entered value kept in the field or the previous car shown in the column, and the comparison table from before the change.
18. IF the employee's Eligibility_Group is unknown (Requirement 5, criterion 7), THEN THE Employee_Screen SHALL disable the car picker and display next to the picker a message in Hebrew that the occupation must be filled in the My Details panel first.
19. THE Employee_Screen SHALL offer in the occupation field of the My Details panel the occupation names of Occupations_Table as suggestions to pick from, while also accepting a name that is not on the list, which the Advisor_Agent then handles according to Requirement 9, criterion 19.
20. WHEN a column of the comparison table has a Family_Track car, THE Employee_Screen SHALL show the employee's share of the gap next to the employer's share.

### Requirement 12: Representative Screen (Rep_Screen)

**User Story:** As the transport representative, I want a screen where I see the questions that the bot sent and answer those questions, without seeing the employee's salary data, documents or conversation, so that the employee's conversation resumes from the same point without emails and without exposing personal information.

#### Acceptance Criteria

1. THE Frontend SHALL display Rep_Screen on a route separate from the route of Employee_Screen, without login (a documented limitation and a need for the pilot, Requirement 17).
2. THE Rep_Screen SHALL display the Rep_Question items with the status `open` before the Rep_Question items with the status `answered`, sort the Rep_Question items within each group by creation time from oldest to newest, and, while no Rep_Question has the status `open`, display in place of the open group a message in Hebrew that there are no open questions, followed by any Rep_Question items with the status `answered`.
3. THE Rep_Screen SHALL display for each Rep_Question the question text, the question type, the creation date and time, the display name and the Eligibility_Group of the Employee (shown as the Hebrew letter, Requirement 16, criterion 1), the relevant car by display name and Official_Key when the Rep_Question has a relevant car, and the status.
4. THE Rep_Screen SHALL display to Transport_Rep only the fields in criterion 3 and the stored answer, so that salary amounts and Net_Pay, the salary and contribution fields of Employee_Profile (base salary, additional pay components, pension, study fund and tax credit points), uploaded documents (Requirement 13) and the Conversation transcript are not displayed in Rep_Screen, including inside the question text, because salary documents are not exposed to anyone else.
5. THE Backend_API SHALL return from the Rep_Screen API routes only the Rep_Question ID, the fields in criterion 3, the Default_Participation of the question's car and the choices of the question (criterion 6), and the answer, without the data that criterion 4 excludes from Rep_Screen and without the Conversation ID, because without login the Conversation ID is enough to open the employee's Employee_Screen.
6. WHILE a Rep_Question has the status `open`, THE Rep_Screen SHALL display next to the Rep_Question an answer form with a submit action and with fields according to the question type: for a question of the Participation type, a numeric Participation amount field in ₪ that accepts 0 or more, a required effective date field and an optional note field, according to Requirement 6, criteria 17-18, where for a car of Car_Catalog the Rep_Screen shows the Default_Participation as the amount of the catalog next to the amount field and fills the field with it, while the effective date field stays empty so that Transport_Rep still confirms the answer; for a question of the occupation type, a required choice among the entries of Occupations_Table; for a question of the eligibility group type, a required choice among the groups א, ב, ג and ד; and for the other type, a required free-text field.
7. IF Transport_Rep submits an answer with a Participation amount that is missing, not a number or negative, with an effective date that is missing or is not a valid calendar date, with no choice or a choice that is not offered, or with free text that is empty or contains only whitespace, THEN THE Advisor_App SHALL reject the answer in both Rep_Screen and Backend_API without storing the answer, keep the Rep_Question with the status `open` and keep the values entered in the form, and display in Rep_Screen next to each invalid field an error message in Hebrew that states what the field requires.
8. WHEN Transport_Rep submits a valid answer to an open Rep_Question, THE Advisor_App SHALL store the answer, mark the Rep_Question with the status `answered`, resume the Employee's Conversation from the same point according to Requirement 10, criteria 7 and 10, and, after the answer is stored, also when resuming the Conversation fails (Requirement 10, criterion 15), display in Rep_Screen a confirmation in Hebrew that the answer was saved, announced to screen readers through an aria-live region.
9. WHILE a Rep_Question has the status `answered`, including right after the confirmation in criterion 8 and before the next reload in criterion 11, THE Rep_Screen SHALL display the stored answer as read-only, without an answer form, according to Requirement 10, criteria 8-9: for the Participation type, the amount in ₪, the effective date and the note when there is one, for the occupation and eligibility group types, the chosen entry or group, and for the other type, the free text.
10. WHEN Transport_Rep reloads the Rep_Screen page in the browser or opens Rep_Screen again, including after a restart of Backend_API (Requirement 10, criterion 14), THE Rep_Screen SHALL load, through Backend_API, from the Database all the Rep_Question items, each with the stored status and answer.
11. WHILE Rep_Screen is open, THE Rep_Screen SHALL reload the list of Rep_Question items from Backend_API at least once every 10 seconds and also when Transport_Rep selects the "Refresh" action (UI copy is Hebrew), so that a Rep_Question created while Rep_Screen is open appears without reloading the page, and the values that Transport_Rep has typed in an answer form and not yet submitted remain in the form, with the keyboard focus kept in the same field.
12. THE Rep_Screen SHALL use the same visual language as Employee_Screen, as defined in Requirement 16, criterion 7, and meet every Requirement 16 criterion that applies to the Frontend or to Rep_Screen.
13. IF submitting an answer fails because Backend_API is unreachable or returns an error other than the rejections in criterion 7 and in Requirement 10, criterion 8, THEN THE Rep_Screen SHALL keep the Rep_Question displayed with the status `open` and keep the values entered in the form, not display the confirmation in criterion 8, and display next to the form an error message in Hebrew that the answer was not saved and can be submitted again.
14. IF a reload of the list according to criterion 11 fails after the list was loaded at least once, THEN THE Rep_Screen SHALL keep displaying the last loaded list and the values typed in answer forms that were not submitted, display a message in Hebrew that the list could not be updated, and remove the message after the next successful reload.

### Requirement 13: Uploading a Payslip or Contract (Optional)

**User Story:** (Optional requirement) As an employee, I want the option to upload a payslip or contract and to confirm the values that were read from the document before the values are saved, so that I save typing without giving up control over my data, while it is always possible to type the data instead.

#### Acceptance Criteria

1. THE Employee_Screen SHALL display an optional action for uploading one payslip or contract file per upload, in PDF, JPG or PNG format with a size of up to and including 10 MB (10,485,760 bytes), and allow the Employee to provide every Employee_Profile field also by typing, in the conversation or in the My Details panel, without uploading a document.
2. IF the Employee uploads a file whose file name extension is not .pdf, .jpg, .jpeg or .png, whose content, checked independently of the extension, is not a PDF, JPG or PNG file (including an empty file), or whose size is larger than 10 MB (10,485,760 bytes), THEN THE Advisor_App SHALL reject the file without sending the file to Document_Reader or to the language model, leave Employee_Profile unchanged and display in Employee_Screen a message in Hebrew with the allowed types and the maximum size.
3. WHEN the Employee uploads a file that passes the checks in criterion 2, THE Document_Reader SHALL read the file using a model with vision capability (OpenAI vision) according to the provider and the model in App_Settings, and extract a candidate value for each of the following fields that appears in the document, and for no other field: the occupation, base salary, additional pay components, the pension contribution percentage, the study fund contribution percentage, tax credit points, and the current car (manufacturer, model and registration year) and the Participation in the current car.
4. IF a field from criterion 3 does not appear in the document, the value of the field is covered, cut off or unreadable in the document, or the value could be obtained only by calculation from other values in the document, THEN THE Document_Reader SHALL leave the field empty and mark the field `not_detected`, without guessing, calculating or completing a value.
5. WHEN Document_Reader finishes extracting values and at least one field was detected, THE Employee_Screen SHALL display to the Employee a confirmation form that lists every field from criterion 3 with the candidate value of each detected field and a marking in Hebrew text for each field marked `not_detected`, offers a "Confirm" action and a "Cancel" action, and allows editing, deleting or completing every value before the confirmation.
6. THE Advisor_App SHALL save values from a document to Employee_Profile only after the Employee selects "Confirm" in the confirmation form, and only the values as they appear in the form at confirmation, so that selecting "Cancel", or refreshing or closing Employee_Screen before confirming, leaves Employee_Profile unchanged, and a field that is empty in the form at confirmation, whether not detected or deleted by the Employee, leaves the stored value in that field unchanged.
7. WHEN the Employee confirms the confirmation form and every confirmed value is valid according to Requirement 11, criterion 3, THE Advisor_App SHALL handle the confirmed values as input from the Employee: save the values and recalculate according to Requirement 11, criterion 4, and identify a car that was read from the document in Usage_Value_Dataset according to Requirement 2, like a car that was typed.
8. THE Document_Reader SHALL return values only for the fields in criterion 3, and no Usage_Value, Net_Pay or other calculated amount, so that Usage_Value is retrieved from Usage_Value_Dataset (Requirement 2) and the Net_Pay of Today and of every Alternative is calculated only in code through Comparison_Engine (Requirement 8), even when the document includes a net pay amount or a usage value.
9. THE Advisor_App SHALL process the uploaded file in memory only and release the file when processing ends (the file is rejected according to criterion 2, Document_Reader returns a result, or reading fails or times out according to criterion 11), without storing in the Database, on disk, in logs or in the message history of the Conversation the file, the file's content or any candidate value that the Employee did not confirm.
10. THE Advisor_App SHALL send the file only to the language model provider defined in App_Settings, and display the candidate values only in the Employee_Screen of the Conversation in which the file was uploaded, so that the file and the values read from the file are not available to Transport_Rep (Requirement 12, criteria 4-5).
11. IF reading the document fails (for example, a damaged or password-protected file), no field was detected in the document, the language model is unavailable, including a missing or invalid API key (Requirement 9, criterion 15), or Document_Reader does not return a result within 60 seconds after the upload of the file completes, THEN THE Employee_Screen SHALL display a message in Hebrew that the document was not read and offer to type the data in the conversation or in the My Details panel, without displaying the confirmation form and without displaying a result that Document_Reader returns after the 60 seconds, with Employee_Profile remaining unchanged.
12. IF the Employee confirms the confirmation form and one or more values in the form are invalid according to Requirement 11, criterion 3, THEN THE Advisor_App SHALL save none of the values from the form, keep the confirmation form open with the values the Employee entered, and display next to each invalid field an error message in Hebrew with the allowed range, with Employee_Profile remaining unchanged.
13. WHILE Document_Reader is reading an uploaded file, THE Employee_Screen SHALL display a message in Hebrew that the document is being read and keep the upload action disabled until the confirmation form (criterion 5) or the message from criterion 11 is displayed.

### Requirement 14: Running, Data Persistence and Infrastructure

**User Story:** As a developer who runs and maintains the system, I want the whole Advisor_App to start with one command, keep its data between runs and report its state through a health route and logs, so that I can run, debug and extend the system without manual setup steps and without exposing salary data or secrets.

#### Acceptance Criteria

1. WHEN a developer runs `docker compose up` on Linux, with no setup step other than copying `.env.example` to `.env` and, optionally, setting the language model's API key in `.env`, THE Advisor_App SHALL start three services: `db`, which runs the Database on SQL Server with a healthcheck that reports healthy only when SQL Server accepts connections; `backend`, which runs Backend_API; and `frontend`, an nginx server that serves the production build of the Frontend and forwards `/api` requests to Backend_API, so that Employee_Screen and Rep_Screen are served at the URLs documented in README.md (Requirement 17, criterion 1).
2. WHEN the `backend` service starts, THE Backend_API SHALL wait until the `db` healthcheck reports healthy, then apply the pending Database migrations, then run the Importer according to Requirement 1, criteria 14-15, and only then start accepting requests under `/api`.
3. IF at startup a required App_Settings variable is missing, empty or has a value that is not valid for the variable's type (for example, a tax year that is not a whole number), connecting to the Database fails, applying the Database migrations fails or the Importer fails, THEN THE Backend_API SHALL exit with a non-zero exit code before accepting requests and log an error message that names the missing or invalid variable, or the failed stage and the reason.
4. THE Codebase SHALL include a `.env.example` file that lists every App_Settings variable that Advisor_App reads, each with a one-line description, whether the variable is required and a placeholder value, with no secret values: the language model's API key has an empty value and the Database password has a sample value for local use only that SQL Server accepts, so that a `.env` file copied from `.env.example` starts Advisor_App according to criterion 1.
5. IF the language model's API key is missing or empty in App_Settings at startup, THEN THE Advisor_App SHALL start without Advisor_Agent, with Backend_API accepting requests according to criterion 2, and serve Employee_Screen, Rep_Screen and the comparison according to Requirement 9, criterion 15, so that the API key is the one App_Settings variable that `.env.example` does not mark as required.
6. WHERE a developer uses dev mode, THE Advisor_App SHALL run the Database in Docker, Backend_API with `uv run uvicorn --reload` and the Frontend on the Angular dev server with a proxy that forwards `/api` requests to Backend_API, as documented in README.md (Requirement 17).
7. THE Database SHALL store each Conversation, with the readable messages and the serialized message history of Advisor_Agent (including the Agent_Tool invocations and results), together with the Employee_Profile, the Alternative items and the Rep_Question items of that Conversation, so that the stored data and the loaded Usage_Value_Dataset remain unchanged after Backend_API restarts and after Advisor_App is stopped with `docker compose stop` or with `docker compose down` without removing volumes, and started again with `docker compose up`.
8. THE Codebase SHALL create and update the Database schema only through versioned migrations that are kept in the Codebase and applied by Backend_API at startup according to criterion 2, with no manual schema changes, so that starting Advisor_App on an empty Database creates the complete schema and starting Advisor_App on a Database already at the latest migration leaves the schema unchanged.
9. WHEN a client requests the health route (`/api/health`), THE Backend_API SHALL respond within 5 seconds, including when the Database is not reachable, with whether the Database is reachable, whether Usage_Value_Dataset is loaded for the tax year defined in App_Settings (that is, the Database has at least one record of that tax year) and the number of loaded records of that tax year, and the catalog cars whose usage value differs from the dataset (Requirement 4, criterion 19), and with HTTP status 200 when both checks pass and 503 otherwise, whatever that list holds.
10. THE Backend_API SHALL write structured logs to standard output (shown by `docker compose logs backend`), as one machine-parseable line of named fields per API request, with the timestamp, the HTTP method, the route, the response status and the duration in milliseconds, and one such line per Agent_Tool invocation, with the timestamp, the Agent_Tool name, the duration in milliseconds and whether the invocation succeeded or failed, each line including the Conversation ID when the request or invocation belongs to a Conversation, so that a developer can trace a Conversation and the Agent_Tool invocations in that Conversation.
11. THE Advisor_App SHALL exclude from the logs of all its services salary amounts and Net_Pay amounts, the salary and contribution fields of Employee_Profile, uploaded documents and the values read from documents (Requirement 13, criterion 9), and secrets, namely the language model's API key and the Database password, including inside a Database connection string, so that searching the logs of all Advisor_App services for a salary amount, a Net_Pay amount or a secret value used in a Conversation finds no match.
12. THE Advisor_App SHALL operate without third-party telemetry, with no Advisor_App service and no Frontend page sending logs, usage data or diagnostic data outside Advisor_App, so that logs and usage data stay within Advisor_App and, once the services have started, the only external destination that Advisor_App sends data to is the language model provider defined in App_Settings.
13. THE Codebase SHALL be a git repository with a `.gitignore` file that excludes `.env`, `node_modules`, `.venv`, build output, `.kiro/handoff` and the challenge PDF, and does not exclude `.env.example` or the Usage_Value_Dataset CSV file in the `data/` folder, so that `git status` lists no untracked file after the Frontend is built and the tests and lint run (Requirement 15, criterion 5).
14. THE Codebase SHALL keep the Usage_Value_Dataset CSV file, with content identical to the provided Tax Authority file (windows-1255, 77,988 records), in the `data/` folder under an ASCII file name, which is the dataset path that `.env.example` sets in App_Settings.
15. IF, during `docker compose up`, the `db` service exits before its healthcheck reports healthy, or the healthcheck does not report healthy within 120 seconds after the `db` service starts, THEN THE Advisor_App SHALL report in the output of `docker compose up` that the `db` service failed, without starting the `backend` service.
16. THE Advisor_App SHALL expose every port it opens on the host only on the host's loopback interface, in the `docker compose up` run and in dev mode, so that Employee_Screen and Rep_Screen, which have no login (Requirement 17, criterion 10), Backend_API and the Database cannot be reached from another machine on the network.

### Requirement 15: Code Quality and Tests

**User Story:** As a developer who maintains and extends the system, I want each layer in its own module, typed and linted code, and offline tests for every challenge rule example, so that I can change a rule or add a feature and confirm with one command that nothing broke.

#### Acceptance Criteria

1. THE Codebase SHALL keep each layer in its own module, with no module that contains code of more than one layer: data access and the Importer, Rules_Config loading, the pure engine (Eligibility_Checker, Payroll_Calculator, Comparison_Engine and Explanation), Advisor_Agent with the Agent_Tool functions, Backend_API, and the Frontend.
2. THE Codebase SHALL keep the pure engine independent of the Backend_API, Advisor_Agent, and data access and Importer modules (criterion 1), so that the pure engine imports nothing from those modules, reads no file, environment variable, network resource or Database, and receives all inputs as arguments.
3. THE Codebase SHALL include type annotations on every parameter and return value of every function and method definition in the Python code, and check the Python code with ruff for both lint and format, so that the ruff lint check and the ruff format check report no violations.
4. THE Codebase SHALL compile the Frontend with TypeScript strict mode enabled and no compile errors, and check the Frontend with the Angular lint and format setup (angular-eslint for lint and Prettier for format), so that the lint check and the format check report no violations.
5. WHEN a developer runs the single check command documented in README.md (Requirement 17), THE Codebase SHALL run the Python and Frontend lint and format checks (criteria 3-4), all pytest tests and all Frontend unit tests, and exit with exit code 0 only if every check and test passes, or with a non-zero exit code if any check or test fails or cannot run.
6. THE Codebase SHALL use English for code, identifiers, comments, logs and commit messages, and Hebrew only in user-facing copy (Requirement 16), in data values copied from Usage_Value_Dataset and in the Explanations_File.
7. THE Codebase SHALL use idiomatic and consistent naming, so that Python names follow PEP 8, TypeScript names follow the Angular style guide and each Glossary concept has the same English name in every layer, with a comment only where the comment states a reason that the code itself does not show, and with no narration comments (comments that restate what the code does), no banner separator comments and no emoji.
8. THE Codebase SHALL contain only code that a feature or a test uses, with no dead code (code that no feature or test executes or references), no TODO comments and no abstraction whose only purpose is a need that this requirements document does not state.
9. THE Codebase SHALL include pytest unit tests for each challenge rule example: in Family_Track, a Car_Budget of ₪3,500 and a Car_Cost of ₪6,000 give ₪1,250 for the employer and ₪1,250 for the Employee (Requirement 6, criterion 6); an Employee in group D may choose a group C car, and an Employee in group C may not choose a group D car; an Alternative with an electric Powertrain adds an EV_Refund of ₪250, and an Alternative with a hybrid, plug_in or conventional Powertrain adds no EV_Refund; Unused_Budget is not paid as salary, so that two Alternatives with the same Usage_Value, Powertrain and Participation and different Car_Cost values below Car_Budget give the same Net_Pay; giving up the car is allowed for an occupation that Occupations_Table permits and not allowed for an occupation that Occupations_Table does not permit; Car_Lookup by Official_Key returns exactly one record; and Car_Lookup by a trade name alone returns 2 or more candidates.
10. THE Codebase SHALL include pytest unit tests that derive Powertrain (Requirement 1, criterion 6) from at least one row of each model below, taken from the Usage_Value_Dataset CSV file, and check that Tesla Model 3, Tesla Model Y, Hyundai Ioniq 5, BYD Atto 3, Volvo EX30, Volkswagen ID.4, Toyota bZ4X and Kia Niro EV are electric, and that the hybrid and plug-in versions of the Toyota Corolla and the Toyota Prius are not electric.
11. THE Codebase SHALL include pytest unit tests that run Payroll_Calculator on every fixture of Requirement 7, criterion 15, including a fixture added as data only, and check that Net_Pay and every breakdown component (Requirement 7, criterion 13), rounded to whole shekels (Requirement 7, criterion 12), equal the manually checked expected values of that fixture.
12. THE Codebase SHALL test Advisor_Agent with the Pydantic AI test and function models instead of a live OpenAI model, covering: asking the Employee only for the missing Employee_Profile fields, so that Advisor_Agent asks for every missing field and for no field that already has a value in Employee_Profile; sending a Rep_Question instead of guessing missing information, so that for a field the Employee cannot provide, Advisor_Agent invokes the Agent_Tool that sends a Rep_Question and the reply contains no value for that field (Requirement 9, criterion 6); every amount in a reply of Advisor_Agent coming from an Agent_Tool result, so that each number in the reply appears in an Agent_Tool result of the same test (Requirement 9, criterion 5); and the scenario of a group B Employee who gives up the car, so that Advisor_Agent invokes Eligibility_Checker and Comparison_Engine and the reply states only the decision, reason and amounts that those Agent_Tool results return.
13. THE Codebase SHALL include Frontend unit tests for rendering the comparison table with a Today column, a column for each Alternative and a row for each item of Requirement 8, criterion 5 (Requirement 11, criterion 5); for validation in the My Details panel, with at least one rejected value of each kind listed in Requirement 11, criterion 3 and at least one accepted value; and for validation of the answer form in Rep_Screen (Requirement 12, criterion 7), with at least one rejected and one accepted answer.
14. WHILE there is no network access and App_Settings has no OpenAI API key, THE Codebase SHALL run all tests of the check command (criterion 5) to completion once the Python and Frontend dependencies are installed, with the same pass, fail or skip outcome for each test as with network access.

### Requirement 16: Design and User Experience

**User Story:** As an employee and as the transport representative, I want a clear Hebrew right-to-left screen that looks like an internal Strauss HR tool, with amounts that are easy to read and full keyboard and screen reader support, so that I can read the comparison and act on it without confusion.

#### Acceptance Criteria

1. THE Frontend SHALL render Employee_Screen and Rep_Screen right-to-left first, with `lang="he"` and `dir="rtl"` on the document, and display all user-facing copy in Hebrew, including headings, labels, buttons, status texts and messages, and each Eligibility_Group as the Hebrew letter defined in the Glossary, while car names and Official_Key values are displayed as they appear in the source data.
2. THE Frontend SHALL bidi-isolate every number, amount, date and Official_Key that appears inside Hebrew text, including in the Explanation and in messages from Advisor_Agent, so that each isolated value displays its digits, sign and ₪ symbol in the same left-to-right order as in criteria 3 and 5 (for example +₪210 and not ₪210+).
3. THE Frontend SHALL display every amount, except a value that the user is typing in an input field, in whole shekels rounded according to Requirement 7, criterion 12, with the ₪ symbol before the number and a comma as the thousands separator (for example ₪950 and ₪12,345).
4. THE Frontend SHALL display the numbers in every table, including the comparison table, with tabular numerals and with the amounts in each column aligned to the same edge, so that the digits of amounts line up in each column.
5. THE Frontend SHALL display every difference from Today and every component of its breakdown (Requirement 8, criterion 6) that is shown as a number, such as in the comparison table, with an explicit sign, a plus sign (+) for an increase in Net_Pay and a minus sign (−) for a decrease (for example +₪210 and −₪120), and a value of zero as ₪0 without a sign, in addition to any color, while a Hebrew sentence that states the direction in words, such as the Explanation (Requirement 8, criteria 9-10), shows the amount in absolute value.
6. THE Frontend SHALL use a self-hosted Hebrew font that the `frontend` service serves, applied to all text of Employee_Screen and Rep_Screen, so that while either screen is in use the browser loads no font, style sheet, script, icon or image from a host outside Advisor_App, including from a CDN.
7. THE Frontend SHALL apply to Employee_Screen and Rep_Screen the visual language of an internal Strauss HR tool: a restrained neutral palette with one accent color, where colors that only indicate a status (an increase, a decrease or an error) do not count as an additional accent color, and custom SCSS styles, with none of the following: gradients, glassmorphism, emoji or sparkle icons, "AI" badges, hero sections, rounded shadowed cards on every element, or the default look of a component library.
8. WHILE the viewport is 1024 pixels wide or wider, THE Employee_Screen SHALL display the conversation, the My Details panel and the comparison table without horizontal scrolling of the page, using a layout designed for a laptop screen of 1280×800 pixels.
9. WHILE the viewport is narrower than 1024 pixels, THE Employee_Screen SHALL stack the conversation, the My Details panel and the comparison table vertically.
10. THE Frontend SHALL use semantic HTML elements, with headings for the titles of screens and areas, a table with a header cell for each column and each row for the comparison table, and buttons for actions, and give every form field a visible label that is programmatically associated with the field, so that a screen reader reads the label when the field has focus.
11. THE Frontend SHALL allow reaching, operating and leaving every control with the keyboard alone, including the car picker (Requirement 11, criterion 7) and the answer forms in Rep_Screen, with a visible focus indicator on the focused control that has a contrast ratio of at least 3:1 against the adjacent background.
12. THE Frontend SHALL announce new messages from Advisor_Agent and confirmations through aria-live regions, according to Requirement 11, criterion 14 and Requirement 12, criterion 8, so that a screen reader reads each new message or confirmation once, without moving the keyboard focus.
13. THE Frontend SHALL display all text, including placeholder text, text on the accent color and status-colored text such as differences and error messages, with a contrast ratio of at least 4.5:1 against the background of the text.
14. WHILE the content of an area, such as the conversation, the My Details panel, the comparison table, the car picker or the list of Rep_Question items, is loading, has no items or failed to load, THE Frontend SHALL display in place of that content a one-sentence message in Hebrew that names the state, instead of a blank area.
15. WHEN the Frontend displays an error message next to a form field (Requirement 11, criterion 3; Requirement 12, criterion 7), THE Frontend SHALL mark the field as invalid and associate the error message with the field, so that a screen reader reads the error message together with the label when the field has focus.
16. WHEN the Frontend displays a message in Hebrew that reports an error or a failure and is not tied to a single form field (for example Requirement 9, criterion 15; Requirement 10, criterion 15; Requirement 11, criteria 11 and 15; Requirement 13, criterion 11), THE Frontend SHALL announce the message to screen readers through an aria-live region, without moving the keyboard focus.
